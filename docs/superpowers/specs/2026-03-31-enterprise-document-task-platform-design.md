# 企业文档任务协作平台设计

> 当前文档为分段确认式设计稿。每一部分会在用户确认后继续补充，避免一次性写入未收敛方案。

## 1. 项目定位

项目正式定义为：

`一个面向普通员工的企业文档任务协作平台。`

更完整的表述是：

`平台以任务为核心入口，通过多 Agent 自动编排和 MCP 外部系统接入，支持员工在已授权的知识空间中对飞书文档发起审阅与修订任务，生成结构化差异预览，经人工审批后异步写回，并保留全链路审计与回放记录。`

这个定义的关键点包括：

- 不是单纯聊天机器人，而是任务执行平台
- 不是单纯知识库问答，而是文档审阅与修订闭环
- 不是只接一个系统，而是以 MCP 为扩展边界
- 不是单 Agent，而是多 Agent 协作
- 不是直接写回，而是审批后异步执行

## 2. 第一版核心业务闭环

第一版主任务先收敛成一条稳定链路：

1. 用户在平台中浏览已授权的知识空间和飞书文档
2. 选择任务模板，例如“内容审阅与修订”
3. 补充少量任务要求
4. 平台自动拆解任务并调度多个 Agent
5. 通过 MCP 读取飞书文档和相关知识
6. 生成修订建议和结构化 diff
7. 用户或审批人查看变更预览
8. 审批通过后，后台异步执行写回
9. 平台记录执行结果、审计日志和任务回放

## 3. 核心模块划分

第一版按 6 个稳定模块设计：

### 3.1 任务入口层

负责任务模板、目标文档选择、任务创建、任务状态页和聊天辅助入口。

### 3.2 任务编排层

负责把用户请求转成标准任务，并调度多个 Agent 和 MCP 工具。这里是平台的核心调度边界。

### 3.3 Agent 协作层

第一版至少拆成这些角色：

- `Planner Agent`
- `Retriever Agent`
- `Review Agent`
- `Edit Agent`
- `Execution Agent`

### 3.4 MCP 连接器层

第一批接飞书文档，但接口设计成通用连接器模型，后续可以继续接 Confluence、Notion、语雀、工单系统等。

### 3.5 知识与检索层

负责知识空间、文档索引、检索、citation 和历史上下文支持。它既服务问答，也服务修订任务。

### 3.6 审批与审计层

负责高风险写操作审批、差异预览、执行确认、审计记录和任务回放。

## 4. 模块拆分原则

这样拆分的目标是：

- 前台产品入口清晰，普通员工能直接用
- 平台内部自然承载多 Agent 协作
- 飞书只是第一个连接器，不会绑死系统边界
- 后续接更多外部系统时，只扩连接器和任务模板，不推翻主架构

## 5. 多 Agent 职责划分

### 5.1 为什么要拆成多 Agent

这个项目里的多 Agent 不是为了增加概念复杂度，而是因为任务天然分阶段，而且每个阶段目标不同：

- 有的阶段负责理解任务
- 有的阶段负责检索证据
- 有的阶段负责审阅判断
- 有的阶段负责生成修订提案
- 有的阶段负责真正执行写回

如果全部塞进一个 Agent，会导致 prompt 过大、职责混乱、审计困难、失败恢复困难，以及审批边界不清晰。

### 5.2 第一版推荐的 Agent 角色

第一版至少拆成以下 5 个角色：

- `Planner Agent`
- `Retriever Agent`
- `Review Agent`
- `Edit Agent`
- `Execution Agent`

#### `Planner Agent`

负责理解任务模板和用户补充要求，把请求拆成标准执行计划。它不直接修改文档，只负责“怎么做”。

#### `Retriever Agent`

负责从知识空间、索引和飞书文档中取证据，返回检索结果和 citation。它不负责最终结论，只负责“找到依据”。

#### `Review Agent`

负责根据证据判断当前文档哪里有问题、哪些内容需要修订、修订原因是什么。它不直接写回，只负责“审阅判断”。

#### `Edit Agent`

负责把审阅结论转成结构化修订提案，包括 diff、修改说明和修订后预览。它不直接执行写回，只负责“产出变更提案”。

#### `Execution Agent`

负责在审批通过后调用 MCP 写回飞书文档，并记录执行结果。它不参与内容判断，只负责“按批准结果执行”。

### 5.3 推荐的执行链路

典型任务的流转建议如下：

1. 用户发起“文档审阅与修订”任务
2. `Planner Agent` 生成执行计划
3. `Retriever Agent` 拉取飞书文档内容和知识证据
4. `Review Agent` 输出审阅意见
5. `Edit Agent` 生成结构化差异预览
6. 平台进入审批状态
7. 审批通过后，`Execution Agent` 调用 MCP 写回
8. 结果进入任务回放和审计记录

## 6. MCP 接入边界

### 6.1 MCP 的位置

`MCP` 应放在连接器层，而不是散落在各个 Agent 内部。

也就是说：

- Agent 不直接面向飞书 API
- Agent 只调用平台定义好的连接器能力
- 连接器内部再通过 MCP 与飞书文档系统通信

这样做可以保证飞书只是第一个连接器，而不是系统内的特殊逻辑。

### 6.2 第一版飞书连接器的能力边界

第一版飞书文档连接器建议暴露以下能力：

- 浏览已授权空间和文档
- 读取文档元数据
- 读取文档正文内容
- 获取文档结构或块信息
- 生成待写回的目标定位信息
- 执行修改已有文档内容
- 返回写回结果和变更状态

飞书连接器只负责“如何和飞书交互”，不负责“该不该改、改什么”。

### 6.3 连接器层的统一抽象

为了方便后续接入其他系统，连接器层统一抽象成三类接口能力：

- `Resource Discovery`
- `Resource Read`
- `Resource Write`

它们分别对应：

- 发现资源，例如空间、目录、文档列表
- 读取资源内容，例如正文、元数据、结构
- 对资源执行受控写操作，例如更新文档内容

未来接入 Confluence、Notion、语雀等系统时，应复用这套能力抽象，而不是把平台写成飞书特化版本。

### 6.4 这一部分的设计结论

- 多 Agent 要按职责拆分，不做大一统 Agent
- MCP 应放在连接器层，不直接散落到 Agent 内
- 飞书是第一批连接器，但平台抽象必须是通用的读写资源模型
- 所有写操作都走“提案 -> 审批 -> 执行”链路

## 7. 任务模型、审批模型与异步执行模型

### 7.1 为什么这一层必须先定义

前两部分解决的是“系统做什么”和“谁来做”，这一部分解决的是：

- 系统里的核心实体是什么
- 一个任务如何流转
- 审批卡在哪一步
- 后台异步执行如何与前台状态对应

如果这部分不先设计清楚，后续实现会很快出现任务记录、审批记录、聊天消息混杂，Agent 状态难恢复，写回失败难补偿，以及回放不完整的问题。

### 7.2 第一版推荐的核心对象

第一版至少定义以下核心对象：

- `Task`
- `TaskStep`
- `TaskArtifact`
- `Approval`
- `ExecutionJob`

#### `Task`

平台中的主任务对象，代表一次完整的文档审阅与修订流程。

#### `TaskStep`

任务中的步骤，对应一次规划、检索、审阅、生成提案、审批、执行等阶段。

#### `TaskArtifact`

任务过程中产生的结果物，例如检索证据、审阅结论、diff 预览、修订后预览、执行结果。

#### `Approval`

高风险操作审批对象。独立于任务，但与任务强关联。

#### `ExecutionJob`

后台异步执行对象，负责真正执行写回、重试、失败记录和结果回传。

推荐的对象关系如下：

- 一个 `Task` 包含多个 `TaskStep`
- 一个 `Task` 可以产生多个 `TaskArtifact`
- 一个 `Task` 在进入写回阶段时，最多挂一个当前生效的 `Approval`
- 一个通过审批的写回动作，会生成一个 `ExecutionJob`

### 7.3 推荐的任务状态机

第一版建议将 `Task` 状态控制在以下范围：

- `pending`
- `planning`
- `retrieving`
- `reviewing`
- `draft_ready`
- `awaiting_approval`
- `executing`
- `completed`
- `failed`
- `cancelled`

这些状态已经足够覆盖第一版完整闭环，并且便于前台展示和后续审计。

### 7.4 审批模型

审批对象应独立建模为 `Approval`，而不是嵌在任务字段中。

第一版的 `Approval` 至少应包含：

- `approval_id`
- `task_id`
- `target_type`
- `target_id`
- `preview_payload`
- `status`
- `requested_by`
- `approved_by`
- `approved_at`
- `comment`

其中最关键的是 `preview_payload`，因为审批的核心并不是一句“是否同意”，而是审批一份明确的变更提案。

### 7.5 异步执行模型

所有真正的写回操作都不应在审批接口中同步执行，而是统一走独立的 `ExecutionJob`。

推荐的执行链路如下：

1. 任务生成修订提案
2. 审批通过
3. 系统创建 `ExecutionJob`
4. 后台 Worker 拉取 Job
5. 调用 `Execution Agent` 和 MCP 写回飞书文档
6. 写回结果更新回 `Task`、`TaskArtifact` 和审计记录

这样设计的好处是：

- 审批接口响应快
- 写回失败可以重试
- 后续接更多系统时可复用同一套后台执行模型
- 任务与执行解耦，便于维护和扩展

### 7.6 前台状态展示原则

前台不应只展示聊天消息，而应围绕任务状态展示：

- 当前任务状态
- 当前执行步骤
- 参与的 Agent
- 当前审批状态
- 最近一次执行结果
- 失败原因或重试状态

### 7.7 这一部分的设计结论

- 平台应以 `Task` 为核心对象，而不是以聊天 session 为核心对象
- 审批应建模为独立实体 `Approval`
- 写回执行应走异步 `ExecutionJob`
- 前台必须围绕任务状态展示，而不只是展示对话消息

## 8. 系统架构分层与目录设计

### 8.1 总体分层

系统建议稳定拆分为五层：

- `Web 应用层`
- `任务与编排层`
- `Agent 协作层`
- `连接器与知识层`
- `基础设施层`

拆分原则是让页面、业务编排、Agent、外部系统连接和底层存储各自独立，避免职责混杂。

### 8.2 Web 应用层

这一层由 `Next.js` 承担，但不只是聊天前端，而是平台入口。

建议承载以下页面：

- 首页 / 产品入口
- 任务创建页
- 已授权知识空间与文档浏览页
- 任务详情页
- 审批页
- 任务历史 / 回放页
- 聊天辅助页

这一层只负责：

- 页面路由
- SSR / SEO
- UI 组件
- 表单提交
- 任务状态展示
- SSE / 轮询消费任务进度

### 8.3 任务与编排层

这一层位于 `Go` 后端内部，是平台最核心的业务层。

它负责：

- 接收任务创建请求
- 生成 `Task`
- 把任务分发给相应工作流
- 驱动多个 Agent 协作
- 控制审批点
- 创建异步执行 Job
- 汇总每一步产物并更新任务状态

建议进一步细分为：

- `task service`
- `workflow orchestrator`

### 8.4 Agent 协作层

这一层负责实际的智能处理能力，但依赖任务编排层调度，不直接暴露给前端。

建议按以下角色划分：

- `planner`
- `retriever`
- `review`
- `editor`
- `execution`

每个 Agent 都只负责单一职责，并通过清晰输入输出交互。

### 8.5 连接器与知识层

这一层承载两类能力，但边界必须区分：

- `MCP 连接器子层`
- `知识与检索子层`

两者的职责分别是：

- 连接器层负责和外部系统交互
- 知识层负责把数据组织成可检索知识并返回证据

### 8.6 基础设施层

这一层负责通用支撑，不参与业务决策，建议包括：

- PostgreSQL
- pgvector
- 本地文件存储
- 后台 Job Worker
- 日志与审计
- 配置管理
- 鉴权中间件

推荐仓库结构如下：

### 8.8 这一部分的设计结论

- 前端是平台入口，而不是单一聊天页
- 后端核心是任务编排层，而不是单一 Agent
- Agent、连接器和知识层必须清晰分离
- 目录设计要围绕 `task + connector + approval + job` 组织，而不是只围绕 RAG

## 9. 数据模型与核心 API 边界

### 9.1 数据模型设计目标

第一版数据建模的目标不是一次性覆盖所有未来场景，而是先固定平台最关键的实体，确保：

- 任务可以完整追踪
- 审批可以独立查询
- 外部资源有统一映射
- 多 Agent 过程结果能落地
- 后续接入其他系统时不用推翻主模型

### 9.2 第一版核心实体

#### `users`

平台用户实体，普通员工和审批人都归在这里。

建议核心字段：

- `id`
- `email`
- `name`
- `role`
- `status`
- `created_at`

#### `knowledge_spaces`

已授权知识空间，用于表示平台可访问的受控知识域。

建议字段：

- `id`
- `name`
- `source_type`
- `external_space_id`
- `status`
- `created_by`
- `created_at`

#### `resources`

统一资源表，用于映射外部系统资源，例如飞书文档。

建议字段：

- `id`
- `space_id`
- `connector_type`
- `external_resource_id`
- `title`
- `resource_type`
- `status`
- `last_synced_at`

#### `tasks`

平台主任务表。

建议字段：

- `id`
- `template_type`
- `status`
- `initiator_id`
- `space_id`
- `resource_id`
- `input_payload`
- `current_step`
- `created_at`
- `updated_at`

#### `task_steps`

任务步骤记录表。

建议字段：

- `id`
- `task_id`
- `step_type`
- `agent_name`
- `status`
- `input_payload`
- `output_payload`
- `started_at`
- `finished_at`

#### `task_artifacts`

任务产物表。

建议字段：

- `id`
- `task_id`
- `artifact_type`
- `content`
- `metadata`
- `created_at`

第一版至少会存储：

- citation 列表
- 审阅结论
- diff 预览
- 修订后全文预览
- 执行结果

#### `approvals`

审批记录表。

建议字段：

- `id`
- `task_id`
- `target_type`
- `target_id`
- `preview_payload`
- `status`
- `requested_by`
- `approved_by`
- `approved_at`
- `comment`

#### `execution_jobs`

异步执行表。

建议字段：

- `id`
- `task_id`
- `approval_id`
- `job_type`
- `status`
- `attempt_count`
- `payload`
- `result_payload`
- `scheduled_at`
- `started_at`
- `finished_at`

### 9.3 为什么聊天消息不是主模型

虽然系统会保留聊天辅助入口，但不建议把 `sessions/messages` 设计为平台主对象。

更合理的做法是：

- `Task` 作为主模型
- 如需聊天记录，再补 `task_conversations` 或 `task_messages` 作为附属记录

### 9.4 API 设计原则

前后端 API 应按业务对象组织，而不是按底层技术模块组织。

不建议设计成：

- `/api/agent/...`
- `/api/mcp/...`
- `/api/rag/...`

推荐按业务对象组织：

- `/api/spaces/*`
- `/api/resources/*`
- `/api/tasks/*`
- `/api/approvals/*`
- `/api/jobs/*`
- `/api/auth/*`

### 9.5 第一版核心 API 边界

#### 知识空间与资源

- `GET /api/spaces`
- `GET /api/spaces/:id/resources`
- `GET /api/resources/:id`

#### 任务

- `POST /api/tasks`
- `GET /api/tasks`
- `GET /api/tasks/:id`
- `GET /api/tasks/:id/steps`
- `GET /api/tasks/:id/artifacts`
- `GET /api/tasks/:id/stream`

#### 审批

- `GET /api/approvals`
- `GET /api/approvals/:id`
- `POST /api/approvals/:id/approve`
- `POST /api/approvals/:id/reject`

#### 异步执行

- `GET /api/jobs/:id`

#### 聊天辅助入口

如果保留聊天入口，应作为任务附属接口：

- `POST /api/tasks/:id/chat`
- `GET /api/tasks/:id/messages`

### 9.6 这一部分的设计结论

- 平台应围绕 `spaces -> resources -> tasks -> approvals -> jobs` 建模
- 外部文档统一映射到 `resources`
- `Task` 是主对象，聊天是附属对象
- API 应按业务对象设计，而不是按底层技术模块设计

## 10. 前端产品形态与页面结构

### 10.1 前端定位

前端不能继续停留在“一个聊天框 + 一个侧边栏”的知识库 Demo 形态，而应体现为任务协作平台的入口。

用户进入系统后，应该明确感受到：

- 自己在发起任务
- 自己在查看任务执行过程
- 自己在审批高风险操作
- 自己在回看历史任务和执行结果

聊天只是辅助交互方式，而不是产品的主视觉中心。

### 10.2 第一版建议的产品入口

第一版前端主入口建议包括：

- 首页
- 任务创建页
- 我的任务页
- 任务详情页
- 审批中心
- 资源浏览页
- 聊天辅助页

### 10.3 首页

首页更适合做成内部工作台，而不是营销官网。

建议首页包含：

- 顶部全局导航
- 最近可用的任务模板
- 我的待处理任务
- 最近访问的知识空间
- 最近审批动态
- 快速发起任务入口

### 10.4 任务创建页

任务创建页建议分为四个稳定区域：

- `任务模板选择`
- `知识空间与目标文档选择`
- `补充要求`
- `任务预览与提交`

该页面应成为普通员工发起任务的主要入口，而不是简单替代成一个聊天输入框。

### 10.5 任务详情页

任务详情页是平台最核心的页面，建议至少包含以下内容：

- `任务基础信息`
- `任务进度`
- `Agent 执行轨迹`
- `任务产物`
- `审批状态`
- `运行日志 / 回放入口`

### 10.6 审批中心

审批中心应作为独立页面或独立模块，建议包含：

- 待审批列表
- 目标文档信息
- 变更摘要
- diff 预览入口
- 批准 / 拒绝操作
- 历史审批记录

审批应围绕变更内容展开，而不是围绕技术流程展开。

### 10.7 资源浏览页

资源浏览页建议支持：

- 知识空间列表
- 空间下文档列表
- 文档基础信息
- 文档最后同步时间
- 发起任务入口

### 10.8 聊天辅助页

聊天页建议保留，但角色应收缩，只用于：

- 对当前任务进行追问
- 基于当前文档请求解释或补充说明

它不应重新成为系统的主入口。

### 10.9 前端交互原则

第一版前端建议坚持：

- 任务状态优先于消息流
- diff 预览优先于整篇结果
- 审批动作优先清晰，不追求花哨
- 所有关键对象都应可追踪
- 不把内部 Agent 复杂度直接暴露给用户，但保留执行过程可视化

### 10.10 这一部分的设计结论

- 前端应做成平台型任务工作台，而不是聊天 Demo
- 主页面应围绕任务创建、任务详情、审批中心和资源浏览组织
- 任务详情页是产品核心页面
- 聊天页保留，但只是辅助入口，而不是主入口

## 11. 实施优先级与开发路线

### 11.1 为什么必须先排优先级

当前项目已经不是单一知识库页面，而是一个包含多 Agent 编排、MCP 外部系统接入、文档读写、审批、异步执行与回放审计的平台型项目。

这类项目如果不先排优先级，最容易出现两类问题：

- 多条主线同时开发，结果没有一条任务闭环真正打通
- 抽象过早，平台概念很多，但第一版没有可演示闭环

因此开发路线必须坚持：

- 先做单任务闭环，再做平台抽象
- 先做飞书读写闭环，再做多系统扩展

### 11.2 第一阶段目标：跑通最小闭环

第一阶段只聚焦一件事：

`普通员工在已授权空间中选择一篇飞书文档，发起“内容审阅与修订”任务，平台生成 diff，审批通过后异步写回。`

这一阶段必须先打通：

- 用户与空间权限
- 飞书资源浏览
- 任务创建
- `Planner -> Retriever -> Review -> Edit`
- diff 预览
- 审批
- `ExecutionJob`
- MCP 写回
- 任务状态页
- 审计与回放

### 11.3 第二阶段目标：把闭环做稳定

第一条链路跑通后，第二阶段重点不是增加新功能，而是增强稳定性，重点包括：

- 任务失败重试
- Execution Job 重试与幂等
- 更完整的任务回放
- 任务步骤和产物持久化结构优化
- 更好的 diff 展示
- 审批意见记录
- 连接器错误处理
- 飞书写回失败后的补偿与提示

### 11.4 第三阶段目标：扩展任务模板

推荐按以下顺序扩展任务模板：

- 文档内容审阅
- 文档修订建议生成
- 审批后写回
- 基于当前文档的问答解释
- 基于多份证据的修订建议

第二批能力应优先在同一资源类型、同一连接器、同一权限模型中扩展，而不是立刻跨系统。

### 11.5 第四阶段目标：扩展连接器

飞书文档连接器稳定后，再引入第二个外部系统。推荐顺序：

- `Confluence` 或 `Notion`
- 之后再考虑工单系统或 IM 系统

这样可以优先验证 `Resource Discovery / Resource Read / Resource Write` 的抽象是否足够稳定。

### 11.6 第五阶段目标：增强多 Agent

第一版多 Agent 的目标是完成任务闭环，而不是构建过于复杂的自主代理系统。后续增强方向包括：

- 更细粒度的 Planner
- 独立的 Policy / Guard Agent
- 更复杂的 Review 策略
- 多文档任务的父子任务编排
- 更细粒度的失败重试和局部重跑

### 11.7 推荐实施顺序

实际开发建议按以下顺序推进：

1. `Task` 主模型和状态机
2. 已授权空间与飞书文档浏览
3. 飞书连接器读能力
4. 最小 `Planner / Retriever / Review / Edit` 链路
5. diff 预览和任务详情页
6. 审批模型
7. `ExecutionJob` 和后台 Worker
8. 飞书连接器写能力
9. 审计与回放
10. 聊天辅助入口
11. 第二任务模板
12. 第二连接器

### 11.8 第一版明确不优先做的事情

第一版不建议优先做：

- 多连接器并行接入
- 多文档批量任务
- 用户自定义 Agent 编排
- 大而全的权限系统
- 很重的工作流引擎
- 过度优化聊天体验
- 没有闭环前先做平台配置中心

### 11.9 这一部分的设计结论

- 先做“单文档审阅修订 + 审批写回”的最小闭环
- 再做稳定性、重试和回放
- 再扩任务模板
- 再扩第二个连接器
- 多 Agent 和平台抽象都必须围绕已验证的任务闭环演进

## 12. 风险点、权限边界与安全策略

### 12.1 为什么这一层必须先定义

项目一旦包含飞书文档读取、飞书文档写回、普通员工发起任务、审批后执行和多 Agent 自动编排，就不再只是一个智能问答系统，而是一个会直接触碰企业内容和企业数据的执行系统。

因此这一部分不是附加项，而是平台主设计的一部分。

### 12.2 权限边界原则

第一版建议坚持以下四条硬边界：

#### 空间授权优先

普通员工不能对任意飞书文档发起任务，只能对已授权知识空间中的文档发起任务。

#### 读写权限分离

一个用户能读取某空间下文档，不代表他一定能触发写回。第一版至少区分：

- 可浏览
- 可发起任务
- 可审批
- 可执行写回

#### 所有写操作都必须审批

飞书文档写回属于高风险操作。第一版里，所有写回都必须走：

`生成提案 -> diff 预览 -> 审批 -> 创建执行 Job -> 写回`

#### 执行权限不等于审批权限

审批人负责判断“这次变更能不能做”，执行系统负责“按批准结果做”。两者必须严格区分。

### 12.3 MCP 接入的安全策略

第一版建议为连接器层定义统一安全规则：

#### 连接器能力分级

每个连接器都要明确能力等级，例如：

- `read_only`
- `write_requires_approval`

#### 写操作必须带上下文

每一次写回都必须能够关联到：

- 哪个任务
- 哪个审批
- 哪个 diff 提案
- 哪个目标文档

#### 连接器层做最终资源校验

即使上层已经做了权限判断，连接器在真正执行前也要再次校验：

- 目标资源是否存在
- 当前映射是否有效
- 当前用户和审批上下文是否匹配
- 当前写回目标是否仍然对应被批准的提案

### 12.4 Agent 层的风险控制

多 Agent 带来能力，也带来风险。第一版至少要控制以下问题：

#### 无依据修订

`Review Agent` 和 `Edit Agent` 不允许脱离证据直接生成高置信修改。

应强制要求：

- 审阅结论必须引用证据
- diff 预览必须能追溯到 citation 或规则依据
- 证据不足时只能输出“需要人工确认”

#### 步骤越权

`Execution Agent` 只能执行已经审批通过的变更，不能自己重新规划任务或追加修改内容。

#### 重试造成重复写入

一旦 `ExecutionJob` 支持重试，就必须考虑幂等性。第一版至少做到：

- 每个写回动作有唯一执行标识
- 重试前检查目标状态
- 结果落库时标记是否已成功写回

### 12.5 审计策略

第一版至少应记录以下事件：

- 谁浏览了哪个空间和文档
- 谁发起了哪个任务
- 哪个 Agent 在什么时间产出了什么步骤结果
- 生成了什么 diff 提案
- 谁审批了、审批意见是什么
- 哪个 Job 在什么时候写回了什么
- 最终成功还是失败

### 12.6 第一版明确的安全底线

第一版至少守住以下底线：

- 普通员工不能操作未授权空间
- 没有审批记录的写操作不能执行
- 批准的是哪份提案，执行就只能写哪份提案
- 执行失败不能伪装成成功
- 任务、审批、执行三者必须能互相追溯
- 前端展示状态不能替代后端最终权限校验

### 12.7 这一部分的设计结论

- 权限边界必须围绕“空间、任务、审批、执行”四层来设计
- MCP 连接器从第一版开始就要能力分级
- 所有写操作都必须是可审计、可回放、可追溯的
- 多 Agent 带来的风险必须通过证据约束、审批隔离和执行幂等来控制

## 13. 简历表达、项目亮点与落地价值

### 13.1 为什么这一部分需要单独设计

同一个项目，因为表达方式不同，面试官可能把它理解成：

- 一个知识库问答 Demo
- 一个带工具调用的聊天机器人
- 一个真正的平台型工程项目

当前方案的价值在于：它已经不是“RAG + 聊天框”，而是一个带任务模型、审批模型、MCP 连接器和多 Agent 编排的企业协作平台。因此必须提前固定项目亮点，避免后续开发又退回到普通 AI Demo 的表达方式。

### 13.2 推荐的一句话项目介绍

推荐在简历中描述为：

`基于 Next.js、Go、Eino 和 MCP 构建的企业文档任务协作平台，面向普通员工提供飞书文档审阅、修订提案生成、人工审批和异步写回能力，并通过多 Agent 自动编排实现任务执行、回放与审计。`

### 13.3 简历中最值得强调的亮点

#### 任务驱动而非聊天驱动

- 设计了以 `Task` 为核心对象的平台模型
- 聊天只作为辅助入口
- 任务状态、步骤、产物、审批和执行都可追踪

#### MCP 连接器架构

- 通过 MCP 接入飞书文档读写能力
- 将外部系统抽象为统一的 `Discovery / Read / Write` 连接器模型
- 为后续接入 Confluence、Notion 等系统预留扩展边界

#### 多 Agent 协作编排

- 将任务拆分为 `Planner / Retriever / Review / Edit / Execution` 多 Agent 协作流程
- 不同 Agent 分别负责规划、检索、审阅、修订和执行
- 通过任务编排层统一调度，避免单 Agent 职责混乱

#### 人工审批与异步执行

- 设计了 `diff 预览 -> 审批 -> Job 执行 -> 写回结果回传` 的高风险操作链路
- 审批模型与执行模型解耦
- 支持执行结果追踪、失败重试和任务回放

#### 审计与安全边界

- 构建了空间级授权、读写分离、审批隔离和执行幂等机制
- 所有写操作都要求可审计、可追溯、可回放
- 将普通员工、审批人和执行系统的权限边界明确分层

### 13.4 项目的落地价值

这个项目解决的不是“更聪明地回答问题”，而是：

- 企业文档更新长期依赖人工重复阅读和修改，效率低
- 单纯知识问答无法真正推动内容更新闭环
- 平台把“查资料、审阅内容、生成修订提案、审批、写回”串成了一条完整链路
- 既提高文档维护效率，又保留人工审批控制力

可以概括为：

`让企业知识维护从被动查询，升级成可控执行。`

### 13.5 简历中的职责写法建议

如果以后以个人项目写入简历，职责描述建议使用以下方向：

- 设计并实现以 `Task` 为核心的企业文档任务协作平台，支持任务步骤、任务产物、审批记录和异步执行的统一建模
- 基于 `MCP` 接入飞书文档系统，抽象统一的资源发现、资源读取和资源写入接口，为后续扩展多系统接入预留边界
- 构建 `Planner / Retriever / Review / Edit / Execution` 多 Agent 协作链路，实现文档审阅、修订提案生成和审批后写回
- 设计高风险写操作审批机制，支持结构化 diff 预览、人工审批、后台 Job 执行、失败重试和任务回放
- 实现空间级授权、读写分离、执行幂等和全链路审计，提升系统在企业场景下的可控性和可维护性

### 13.6 这一部分的设计结论

- 项目应被定义成企业文档任务协作平台，而不是知识库聊天项目
- 简历亮点要围绕 `任务模型 + MCP 连接器 + 多 Agent 编排 + 审批执行 + 审计安全`
- 项目价值要讲“可控执行闭环”，而不是只讲“智能问答”
